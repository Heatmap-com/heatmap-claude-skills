# experiment-design-and-prioritization

## What this skill enables

This skill gives Claude the complete experiment design and backlog prioritization
methodology: ICE scoring with BDF-grounded confidence inputs, hypothesis writing
standards, the full test design checklist (audience, metric, MDE, sample size,
do-no-harm guardrail, holdout), and three MCP recipes that provide the data
inputs for ICE scoring. After loading this skill, Claude can take a user's list
of test ideas and return a scored, sequenced test roadmap ready to execute.

Source material: *Billion Dollar Websites* Chapters 13, 14, 15; MCP source at
`heatmap-mcp` repository (commit 275e777).

---

## The Optimization Loop

Every CRO program runs the same loop, indefinitely:

1. **Research** (BDF): surveys, user testing, competitor analysis, raw data
2. **Hypothesize**: generate hypotheses from BDF findings
3. **Prioritize**: ICE-score the hypothesis backlog
4. **Design**: write the test spec using the four-element checklist
5. **QA**: verify the test renders correctly on all target devices
6. **Run**: minimum two weeks; maximum two active tests per user journey
7. **Analyze**: RPS primary; CR, AOV secondary; Quadrant-stratified validation
8. **Learn**: update ICE scores; generate follow-up hypothesis; update BDF

Your website always sucks a little more than it will after this loop runs one
more time.

## The ICE Method

### Scoring Dimensions

**Impact (1–5)**

How much revenue lift is this test likely to produce if it wins?

Calibrate by:
- Page traffic: high-traffic pages score higher (error cost is multiplied by volume)
- Element visibility: 100%-visible elements (nav, hero, CTA) score higher
- Funnel position: a funnel step with a 2× above-benchmark drop rate scores 5
- Historical: prior tests in this area produced large lifts → score higher

| Score | Meaning |
|---|---|
| 5 | Could move sitewide RPS by > 5% if it wins |
| 4 | Could move the target page RPS by > 10% |
| 3 | Moderate expected lift; high-traffic page |
| 2 | Small expected lift or low-traffic page |
| 1 | Marginal lift expected; low traffic |

**Confidence (1–5)**

How strongly does the BDF data support this hypothesis?

| Score | Evidence |
|---|---|
| 5 | Customer survey verbatims + heatmap data + screen recording + user test all point to same issue |
| 4 | Two or more BDF sources agree |
| 3 | One BDF source (e.g., heatmap only) supports the hypothesis |
| 2 | Informed intuition from domain expertise; no BDF data yet |
| 1 | "We think this might help" with no supporting data |

**Effort (1–5, inverse)**

How much engineering and design work does this test require?

| Score | Meaning |
|---|---|
| 5 | < 2 hours: copy change, image swap, nav reorder |
| 4 | Half day: small design change, variant in test platform |
| 3 | 1–2 days: new page section, new component |
| 2 | 3–5 days: significant dev work |
| 1 | > 1 week: full page rebuild or complex logic |

### ICE Score = Impact + Confidence + Effort

Maximum possible score: 15. Tests scoring ≥ 12 are Priority 1. Tests scoring
8–11 are Priority 2. Below 8 should be reconsidered — either gather more
evidence to raise Confidence, or narrow scope to raise Effort score.

**Important: Effort should not be the deciding factor.** A test with Impact 5,
Confidence 5, Effort 1 (ICE = 11) should not be skipped in favor of a test
with Impact 2, Confidence 2, Effort 5 (ICE = 9). The highest-ICE tests run
first, regardless of effort.

### Updating ICE After Each Test

After every test concludes:
1. Update Confidence scores for related hypotheses based on the new intel
2. Add follow-up hypotheses generated by the test result to the backlog
3. Re-rank. The order will shift as understanding compounds.

## Writing a Good Hypothesis

Every hypothesis follows this structure:

> "We believe [specific change] on [specific page] will [increase/decrease]
> [RPS/CR/AOV] for [target audience] because [BDF evidence for this belief].
> We expect [estimated % change]."

**Examples:**

Good hypothesis:
> "We believe changing the hero image from a lifestyle photo to a product-on-white
> image on /products/joint-support will increase RPS for First-Time Mobile users
> by 10–15% because 4 of 5 user tests showed confusion about what the product
> looked like, and our exit survey shows 'wasn't sure what I was buying' as the
> #2 reason for not purchasing."

Bad hypothesis:
> "Let's try a better hero image."

The difference: the good hypothesis has a specific change, a specific metric,
a specific audience, and specific BDF evidence. The bad hypothesis is a
direction, not a testable prediction.

**Hypothesis quality check:**
- Does it name the exact element being changed?
- Does it predict the direction of the metric change?
- Does it name the primary metric (RPS)?
- Does it cite at least one BDF data source?
- If it wins, will you know *why* it won (and what to test next)?

## Test Design Checklist (Four Elements)

Every valid test has exactly four elements before it goes live:

### Element 1: The Test

The hypothesis (see above). Includes:
- Specific element being changed
- Expected metric direction and magnitude
- BDF evidence supporting the hypothesis

### Element 2: Target Demographics

**Blanket:** All visitors see either control or variant. Quadrant analysis is
run post-hoc on results. Use blanket when:
- This is a first-run hypothesis with unknown segment behavior
- Traffic volume supports multi-Quadrant analysis within 2 weeks

**Targeted:** Only a specific segment sees the test. MCP filter applied in the
test platform. Use targeted when:
- A prior Blanket test showed a clear segment-specific effect
- You want to maximize statistical power on a known segment
- Traffic is limited and you want to concentrate sessions in the highest-signal Quadrant

### Element 3: Target Webpage

The specific URL. Must be a single page or a clearly defined URL pattern.
Multi-page tests are valid only with URL patterns (e.g., all `/products/*`).

### Element 4: Measurement

- **Primary metric:** RPS (always)
- **Secondary metrics:** CR, AOV, Add-to-Cart rate, time-on-page, scroll depth
- **Minimum duration:** 2 weeks (non-negotiable)
- **Statistical thresholds:** ≥ 95% significance, ≥ 80% power
- **Do No Harm guardrail:** defined before the test launches (see below)
- **Quadrant plan:** which Quadrant cuts will be run at analysis time

## Minimum Detectable Effect (MDE)

MDE is the smallest improvement you'd consider worth implementing. It determines
how long the test needs to run.

**Rule of thumb:** At ≥ 95% significance and ≥ 80% power, with a 50/50 split:
- Detecting a 5% lift requires ~10,000 sessions per variant (20,000 total)
- Detecting a 10% lift requires ~2,500 sessions per variant (5,000 total)
- Detecting a 20% lift requires ~650 sessions per variant (1,300 total)

For sites with < 10,000 sessions/month: test larger changes. A small copy tweak
that produces a 3% lift will never reach significance on a small-traffic site.
Test headline rewrites, not button color changes.

**MCP recipe for baseline calculation:**

```json
// Get baseline sessions and RPS for the test page
{
  "site_id": "<id>",
  "date_range": { "start": "2026-04-01", "end": "2026-04-30" },
  "metrics": ["SESSIONS", "REVENUE_PER_SESSION", "CONVERSION_RATE"],
  "page_url": "/the-page-to-be-tested"
}
```

Use the returned `sessions` to estimate test duration: if the page gets 500
sessions/week, detecting a 10% RPS lift (MDE = 10%) requires
`5,000 total sessions / 500 per week = 10 weeks`. That is too long — either
test a larger change (aim for 15–20% MDE) or run a Live Test.

## The Do No Harm Guardrail

Before launching any test, define the guardrail condition: the threshold below
which you will stop the test early even before 2 weeks.

**Default guardrail:** If RPS drops below `baseline × 0.85` (more than 15%
worse than control) AND the result has > 80% significance of being negative,
stop the test.

Additional guardrails to consider:
- AOV guardrail: if AOV drops > 20%, stop (even if CR improved)
- Add-to-Cart rate guardrail: if ATC rate drops > 25%, stop

The Do No Harm rule is not a replacement for statistical rigor — it is a
circuit breaker for tests that are clearly, confidently hurting the site.
Use it sparingly; stopping tests early for small negative swings destroys
the statistical integrity of the result.

## MCP Recipes for ICE Scoring

### Recipe 1 — Impact scoring inputs: page traffic and baseline RPS

**Question:** How should we score the Impact dimension for tests on different pages?

```json
{
  "site_id": "<id>",
  "date_range": { "start": "2026-04-01", "end": "2026-04-30" },
  "metrics": ["SESSIONS", "REVENUE", "REVENUE_PER_SESSION"],
  "sort_by": "SESSIONS",
  "sort_direction": "DESC",
  "limit": 30
}
```

Parse `table_rows`. For each page:
- `sessions` → determines traffic weight (high sessions = higher Impact potential)
- `revenue_per_session` → compared to site average: pages below 0.5× average
  have highest upside (Impact 4–5)

Assign Impact scores:
- Sessions in top 20% AND RPS below 0.5× site average: Impact 5
- Sessions in top 20% AND RPS near site average: Impact 3–4
- Sessions in bottom 50%: Impact 1–2 regardless of RPS

---

### Recipe 2 — Confidence scoring inputs: funnel-driven evidence

**Question:** A test hypothesis claims that checkout friction is causing drop-off.
How confident should we be?

Run the funnel to confirm the drop exists and quantify it:

```json
{
  "site_id": "<id>",
  "date_range": { "start": "2026-04-01", "end": "2026-04-30" },
  "steps": [
    { "type": "EVENT", "event": "CHECKOUT_STARTED" },
    { "type": "EVENT", "event": "CHECKOUT_COMPLETED" }
  ]
}
```

If `abandoned_rate > 0.50` (above benchmark of 0.30–0.50), confirm with element
data:

```json
{
  "site_id": "<id>",
  "date_range": { "start": "2026-04-01", "end": "2026-04-30" },
  "page_url": "/checkout",
  "order_by": "VALUE",
  "sort_direction": "DESC",
  "limit": 30
}
```

Elements with high `value` (clicks) and low or zero `revenue` on the checkout
page are Conversion Killer candidates. If these exist AND the funnel shows
above-benchmark abandonment: Confidence = 4 (two data sources agree). If you
also have exit survey data showing "hidden shipping costs" as a reason: Confidence = 5.

---

### Recipe 3 — Blanket vs. Targeted decision: identify which Quadrant the test is for

**Question:** Should this test be Blanket or Targeted?

Run the Quadrant baseline for the test page:

```json
// Four separate calls, one per Quadrant, on the target page
// First-Time Mobile:
{
  "site_id": "<id>",
  "date_range": { "start": "2026-04-01", "end": "2026-04-30" },
  "metrics": ["SESSIONS", "REVENUE_PER_SESSION", "CONVERSION_RATE"],
  "filters": { "new_user": true, "device": "MOBILE" },
  "page_url": "/target-page"
}
```

If one Quadrant has both:
- A disproportionate share of sessions (> 50% of total)
- A significantly lower RPS than the other Quadrants

Then use Targeted for that Quadrant to maximize statistical power on the segment
where the effect is most likely. If sessions are spread evenly or the RPS
disparity is not extreme, start with Blanket.

## Decision Rules

1. **Run tests in ICE order, not effort order.** High-effort tests at the top of the ICE list are still the right tests. Low-effort tests with low impact are distractions.
2. **No test launches without a hypothesis.** A hypothesis is specific, cites BDF evidence, and predicts a metric direction. "Try X" is not a hypothesis.
3. **Maximum two active tests per user journey at any time.** More destroys attribution.
4. **Define the Do No Harm guardrail before launching.** It is always RPS-based. Always define it in advance, not during the test.
5. **Blanket first for new hypotheses; Targeted when the segment is known.** Start broad; narrow as intel accumulates.
6. **Update ICE after every test.** New results change the Confidence of related hypotheses. The backlog is a living document.
7. **Every concluded test generates at least one follow-up hypothesis.** Add it to the backlog before moving on.

## Gotchas

**Gotcha 1 — ICE scoring from intuition, not data.**
If your Confidence scores are consistently 1–2 for all hypotheses, you haven't
run the BDF research yet. Fix the research gap before the ICE gap.

**Gotcha 2 — Running the highest-effort test first because it "feels more impactful."**
Effort is an inverse score. High-effort tests score low on Effort. They can
still rank high in ICE if Impact and Confidence are high — but they should never
be run first *because* they're big. Run on ICE score only.

**Gotcha 3 — Setting the MDE too small for your traffic level.**
A 5% MDE on a page with 200 sessions/month requires years to reach significance.
Be realistic about your traffic and set the MDE accordingly. Aim for changes
large enough to produce detectable effects in 2–4 weeks.

**Gotcha 4 — Forgetting to update the ICE backlog after each test.**
The backlog gets stale if it's not updated after each test. Prior high-Confidence
hypotheses may have lower confidence after a related test ran and produced
unexpected results. Live backlog = higher-quality test queue.

**Gotcha 5 — Triggering the Do No Harm guardrail too early.**
The guardrail is for confident, significant negative results — not for "it
looks slightly down on day 5." Normal test variance within the first week
frequently shows negative swings that correct by day 14. Only stop a test early
if the negative signal is both large (> 15% RPS drop) AND statistically
significant (> 80% confidence it's negative).
